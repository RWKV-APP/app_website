# Admin RWKV Chat Handoff

This document preserves the working context behind the `/admin/rwkv-chat` page.
It is intended for future coding agents and maintainers who need to continue the RWKV Chat, batch inference, web search, and persistence work in this repository.

## Current Goal

The admin page should let logged-in admins chat with remote RWKV Lightning models from the website, while preserving enough server-side state to inspect and resume conversations later.

The desired UX is:

- `/admin/rwkv-chat` is only available to authenticated admin users.
- The left side shows a server-backed conversation list.
- The current conversation is highlighted.
- Clicking a conversation loads its message list from the server.
- User messages and assistant messages are persisted.
- Assistant messages preserve their batch state, slot state, references, streamed content, and errors.
- Every new user send creates a new batch group.
- Web search and batch inference default to enabled.
- The `Batch Count` control chooses how many assistant slots the next turn creates.
- Each search provider maps to one batch slot.
- The currently selected slot is saved and used as the assistant history for the next turn.

## Why This Exists

The discussion started from RWKV Chat web search quality and architecture.

The original Flutter app already had a server-maintained internet search feature that returned summaries and URLs. The boss wanted more local/client-side experimentation, including DOM-to-markdown style extraction inspired by Resiliparse and Markdownify pipelines. After comparing approaches, the practical split became:

- Query-to-URL discovery is hard to do fully locally without operating a real search index.
- Full local crawler plus index is too heavy for a desktop app first version.
- Existing search APIs and provider adapters are the practical way to collect top URLs/references.
- The final answer should still be generated by RWKV, not by the search provider's own model answer.
- For experimentation, the website admin page can run many search providers in parallel and compare their grounded RWKV outputs.

This repo is therefore used as a controlled admin workbench for search-provider comparison, RWKV batch inference, and conversation persistence.

## Persistence Model

Prisma models are in `backend/prisma/schema.prisma`:

- `RwkvChatConversation`
- `RwkvChatMessage`
- `RwkvChatBatch`
- `RwkvChatSlot`

The local SQLite database is:

- `backend/prisma/rwkv.app.db`

That database is ignored by git and is runtime data.

Model ownership:

- `RwkvChatConversation`: list item, title, selected message/slot, preview, timestamps
- `RwkvChatMessage`: user or assistant message, status, selected slot, final chosen content
- `RwkvChatBatch`: one RWKV batch run for an assistant message
- `RwkvChatSlot`: one provider output inside a batch, including references, streamed content, status, and errors

Statuses currently used:

- Message/batch: `done`, `running`, `error`, `stopped`
- Slot: `queued`, `searching`, `generating`, `done`, `error`, `skipped`

References are stored as JSON text in `RwkvChatSlot.references`.

## RWKV Lightning

The frontend must not talk directly to RWKV Lightning.
The browser should never receive the Lightning password.

The backend reads passwords from:

- `RWKV_LIGHTNING_7B_PASSWORD`
- `RWKV_LIGHTNING_13B_PASSWORD`
- `RWKV_LIGHTNING_PASSWORD`

Configured endpoints in the current implementation:

- 7.2B: `http://47.115.88.183:1801/v1/chat/completions`
- 13.3B: `http://47.115.88.183:1800/v1/chat/completions`

The backend uses RWKV Lightning V1 style request fields:

- `contents`
- `max_tokens`
- `stop_tokens`
- `temperature`
- `top_p`
- `top_k`
- `alpha_presence`
- `alpha_frequency`
- `alpha_decay`
- `chunk_size`
- `stream`
- `password`

Batch inference uses `contents: string[]`, one prompt per runnable slot.
The streaming response is mapped back by `choice.index`.
The user-facing `Batch Count` is different from `RWKV_CHAT_LIGHTNING_BATCH_SIZE`: `Batch Count` controls how many slots are created, while `RWKV_CHAT_LIGHTNING_BATCH_SIZE` only controls how many runnable slots are sent to Lightning per upstream request.
The backend sends runnable slots to Lightning in chunks controlled by `RWKV_CHAT_LIGHTNING_BATCH_SIZE` and defaults to `4`, because 13B can return a `200 text/event-stream` with an empty body when several longer grounded prompts are sent in one large batch.
If the stream itself is empty, the backend retries the same runnable chunk with `stream: false` and translates the returned JSON choices back into the same `slot_delta` / `slot_done` events.

If both the streaming request and the non-streaming retry return no content for a slot, the backend records:

- `slot_error`
- `RWKV Lightning returned no content for this slot.`

This avoids showing a false successful blank assistant answer.

## Search Providers

Search providers live in:

- `backend/src/rwkv-chat/rwkv-chat.search.ts`

Provider keys currently expected by the UI/backend:

- `rwkv_app_search`
- `rwkv_app_deep_search`
- `qwen`
- `kimi`
- `zhipu`
- `stepfun`
- `qianfan`
- `tencent_wsa`
- `ark_doubao`
- `deepseek_search`

Provider behavior:

- Providers run concurrently.
- Unconfigured providers are marked `skipped`.
- A provider returning no usable references is marked `error`.
- Provider answers are not shown as final answers.
- Only provider references/search results are used to construct RWKV prompts.

Important provider fixes already made:

- `rwkv_app_search` reads title/url/summary from `payload.data[]` directly.
- Kimi needs a second tool-call loop to retrieve web references.
- Qianfan can return zero refs with restrictive recency; retrying with `noLimit` recency fixes this in practice.
- Zhipu may need a higher timeout; local testing used `RWKV_CHAT_SEARCH_TIMEOUT_MS=60000`.

Provider env names are documented in:

- `backend/.env.example`

Do not put real provider keys in tracked files.
Use `backend/.env.local` locally or production runtime environment variables.

## History Semantics

History is now server-backed.

For each user send:

1. The backend resolves or creates a conversation.
2. It creates a persisted user message.
3. It creates a persisted assistant message.
4. It creates a batch record and slot records.
5. It loads recent persisted history for the conversation.
6. It searches providers.
7. It streams RWKV output into slots.
8. It writes terminal message/batch/slot states.

The assistant message content is the selected slot content.
When the user clicks a different slot, `POST /admin-api/rwkv-chat/messages/:id/select-slot` writes the selection back to the server.

The next turn should only use the selected assistant slot as historical assistant context.

## Known Runtime Caveat

During local smoke testing, direct requests to the configured RWKV Lightning 7B endpoint returned:

- HTTP 200
- `content-type: text/event-stream`
- empty streamed content

The admin chat backend handled this as an explicit slot error and persisted that state.
If future tests show blank answers, first verify the upstream Lightning service directly before changing the admin chat persistence or frontend rendering.

## Non-Goals For The Current Version

The first version intentionally does not include:

- persistent multi-user ownership beyond admin session metadata
- conversation search
- pagination beyond the current lightweight list
- provider result caching
- editing message content
- exporting conversations
- background retry jobs
- a public non-admin chat page
- a full local crawler or local web index

These can be added later if the admin workbench proves useful.
